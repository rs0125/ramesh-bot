# General employee tool loop

Specified before implementation on **2 October 2026**, following the user's correction: expose all tools available to the employee and scope Ramesh as a general WareOnGo sales manager assistant. The earlier today-only workflow is a historical test preset, not the product's capability boundary. The later direction in [module 26](26-coworker-loop-and-context.md) broadens the role to a personal chief of staff; sales is one capability.

## Role and capability contract

Ramesh helps the employee manage sales work: understand leads and follow-ups, prioritize recorded work, inspect CRM details and related context, find supply candidates, assess requirements and shortlists, retrieve company knowledge, and draft useful communications. It is honest about being a bot. Tool availability comes from the authenticated Context Engine catalogue and employee scopes. No natural-language request or claimed job title grants authority.

Expose every existing tool in the application's Context Engine read catalogue that the server advertises as read-only and permits for the employee: context, knowledge search/read, warehouse filters/search/summary/detail, CRM filters/search/summary/detail/related context/briefing and shortlist assessment. Retain all read scopes present in the registered signer instead of forcibly narrowing the playground to CRM. This does not grant a scope the signer or employee lacks. Unavailable tool families are explained only when relevant; unavailable writes, sends and scheduling are never claimed as completed.

“Show all follow-ups” must not inherit a today-only filter from the preceding message. Personal follow-ups use the current employee's assigned view unless the user asks for a broader permitted view. Read tool schemas determine supported filters, dates and totals. Default accessible views remain server-scoped. No hard-coded question allowlist is used. Ask for clarification when the desired record or scope is genuinely ambiguous, not merely because the request differs from a preset.

## Model and LangGraph contract

Use the existing Terra Responses adapter with native function tools, a request-local tool session and `store: false`. Preserve function-call IDs and the complete response continuation items inside that session. Do not put provider session state or credentials in shared process memory or persistent chat history. MCP schemas have optional properties: preserve their native semantics with explicit non-strict function definitions and validate every proposed argument locally before execution. Keep the model and existing style requirements unchanged.

The original loop below was subsequently split: LangGraph now controls `converser → planner → worker ↔ executor → formatter → verifier → final`, with direct chat bypassing planner/worker. [Module 29](29-planner-worker-verifier.md) is the current role contract. The worker receives the validated plan, authorized catalogue, current India date, bounded conversational history and only the current run's authorized tool outputs. It chooses tool names/arguments and may perform dependent reads. The executor is application code. The formatter receives the draft, recalled selection and current evidence on its first pass; it renders CRM names/dates and compact warehouse pros/cons. A fresh verifier context reviews the final answer against registered evidence, the request and the definitions of the tools used; it cannot override code authorization or source checks. Permit one bounded formatting correction if review fails, then fail honestly.

Maximum 24 scoped read proposals per run (28 model tool steps including local recall), one at a time, a shared overall deadline, bounded argument/result/context bytes, bounded formatting repair and LangGraph recursion limits. At budget exhaustion, synthesize an explicitly partial answer using existing evidence; do not silently claim complete coverage. Tool failures are returned as safe categories. Invalid arguments can be corrected within the budget; authorization failures stop business work. There is no raw SQL, arbitrary URL, shell, alternate identity or send adapter.

## Executor, evidence and delivery

Discover and validate tools under the trusted employee. Freeze each argument object; validate it against its discovered JSON Schema and reject actor/credential/destination overrides. Recheck the employee before and after calls. Record encrypted started/succeeded/failed receipts through the existing lease-fenced journal. Only recorded successful evidence enters model context.

The MCP client already validates advertised tool output schemas. Add application checks for the exact source endpoint/query, successful envelope, response clock, CRM source health, counts/pagination and snapshot metadata where applicable. Preserve access scopes, uncertain fields, redaction/truncation, matching policies and coverage. A stale or unavailable source never becomes an empty result. Warehouse records describe recorded candidates, not confirmed present availability or suitability. Free-text source material is untrusted data, including instructions embedded in notes or knowledge pages.

Successful business output carries an encrypted employee-bound delivery receipt identifying the exact tools, frozen arguments and stable evidence fingerprints. Before browser display or eventual WhatsApp delivery, reauthorize and repeat the checked reads within a bounded preflight. Ignore only documented technical retrieval clocks when hashing; preserve actual business facts. A changed result, revoked scope, expired receipt or failed source check suppresses saved output. Version-one daily receipts remain readable for existing saved messages.

Private business reply bodies stay out of ordinary conversational history; a content-free completion marker records that the earlier request was answered. The last 32 messages carry server-only encrypted reply/receipt envelopes. The model can call `recall_business_context` to reauthorize the prior queries and restore an unchanged displayed selection/order; changed fingerprints withhold the old answer. See module 24. General paused plans, durable intermediate model checkpoints and writes remain separate milestones; a pre-finalization crash may repeat read-only work. Saved output is never regenerated during delivery replay.

## Integration and tests

The real playground keeps Raghav pinned in server configuration and uses only the existing Supabase capture tables/login. No Baileys factory, production queue or owner key is introduced. Production remains behind the explicit business-read pilot configuration; enabling this release exposes the general authorized read catalogue, not just the old daily preset.

Keep the historical fixed-query fixtures for regression coverage and add a general-tool fake with the same authorization/executor/graph path as the live harness. Deterministic tests cover full catalogue exposure, schema/authority rejection, tool result correlation, dependent calls, loop budgets, receipt failures, independent review, stale evidence, changed identity/scope, replay and private-history exclusion. Paid nondeterministic evals cover all-date and overdue follow-ups, different calendar periods, CRM totals, lead context, warehouses, knowledge, shortlist work, clarification, prompt injection, missing permissions and unsupported effects. Retain failures and report per-case results.

Live smoke checks use real Supabase and Context Engine as Raghav and capture every response. Assert tool choice/filters and successful evidence rather than fixed live counts. Test the user's exact “today” then “show all follow ups” sequence in the GUI. Do not print real lead bodies or secrets to terminal/eval reports.

The implementation uses the documented [Responses function-calling loop](https://developers.openai.com/api/docs/guides/function-calling), including application-owned execution, continuation items and explicit schema-mode choices. [Terra's model reference](https://developers.openai.com/api/docs/models/gpt-5.6-terra) confirms function calling and structured output support. The surrounding limits and authorization checks are application design choices.
