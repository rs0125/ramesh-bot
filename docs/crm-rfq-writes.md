# CRM RFQ write integration

Context Engine owns `create_crm_rfq`, its intake SOP, `crm.rfq:write` permission and the Twenty adapter. Ramesh uses the existing generic business-write executor. This branch adds optional `sourceTextArgument` metadata so domains can require complete source text in a specified argument.

New inbox messages and captions now retain leading/trailing whitespace during WhatsApp mapping, so the encrypted source matches the incoming text. Greeting-only normalization is unchanged. Older inbox records retain whatever text was previously stored; missing historical whitespace cannot be reconstructed.

For RFQs that argument is `raw_text`. Ramesh hides it from the model's input schema and fills it directly from the complete stored text selected by `_source_message_ids` / `write_sources`. This happens before persistence, hashing and independent verification. Multiple messages join in selection order with two newlines. Whitespace and `#twenty` tags are retained; a model-supplied replacement is rejected. Source length and content constraints are checked before a proposal is stored, without truncation. Without explicit selection, the current authorized source is used; when it is a WhatsApp reply ("Add to crm" on an earlier brief), the replied-to message comes first, then the request. If the replied-to message cannot be read, nothing is staged and Ramesh asks the user to forward or paste the brief rather than saving the request text alone. Historical/forwarded sources provide data and cannot authorize a write.

Current direct-message authorization, independent verification, the encrypted journal and frozen UUID/arguments remain in charge. A clear direct request creates the RFQ in the same turn, after review, and returns an authoritative concise receipt. It does not show the internal JSON preview or ask for a second confirmation code. Ambiguous intent, source brief or an essential unsupported action still needs clarification. Missing extracted fields do not.

The RFQ tools do not grant generic journal redisclosure: a create grant cannot reveal rich CRM history. RFQ edits and undo must be restricted in Context Engine to records this agent created for the current employee; other CRM records remain unavailable for editing. A broader confirmation-based flow is deferred. Domain-owned receipt lookup and current record authorization must establish the target rather than enabling `auditHistory: actor_scoped` for CRM.

Creation requires only the complete original brief and the runtime-managed operation UUID. Location, requirement, company, contact, budget, duration, source and repeat-client status are all optional. The full raw message becomes `description`; incomplete and informal briefs can be saved without extracting anything. Unsupported enrichment is left out of structured fields while its source remains intact in the description. New records always start at `RFQ_RECEIVED`.

The planner, worker and reviewer must not turn capture into a questionnaire or demand exhaustive extraction. They retrieve the actual original brief when a later “yes” authorizes saving it. A save receipt uses the returned CRM title and verified link and confirms preservation of the full brief; it does not present proposed optional fields as successfully saved. Missing values, unfamiliar size wording or unsupported phone formats do not require cancellation and resubmission. Exact numeric area and supported phone enrichment remain conservative, without blocking capture.

For a request entirely covered by a new RFQ receipt, `responseMode=receipt_only` skips the supplemental formatting model call. The application presents the exact staged intent to the independent reviewer and returns its code-generated receipt only after finalization. Mixed requests, material explanations and reviewer repairs keep normal composition. The presentation hint never supplies authorization or proves a save. Strict provider tool arguments decode to the same original business payload; optional intake values remain omittable and nullable edit fields retain a separate explicit-clear representation.

Edit receipts list every supported changed detail, including title/company, lead source, lease duration and repeat-client Yes/No. Explicit null is shown as cleared; omitted fields are not listed. Classification values have readable labels. A fresh authenticated `description_unchanged` comparison confirms that this edit left the description unchanged, or reports a difference for checking in CRM. Missing comparisons and replayed receipts make no description-preservation claim. This does not claim equality with the original chat or that earlier edits never occurred.

RFQ read text marked `representation: normalized_display` is a cleaned display, including when `redacted=false` and `truncated=false`. Worker, formatter and reviewer must not infer lost stored whitespace or exact-original preservation from that projection. Exact-original claims require comparison evidence; ordinary keep-the-brief requests do not need a formatting audit. These additions do not change source storage, masking, authorization, or the edit payload.

Internal supply contacts are not automatically client contacts, and named roles in the brief do not change CRM ownership. Explain material assignment limitations and clarify only when an essential requested action cannot be performed. Edits retain their current-value, version and clearing safeguards. See the [validation audit](validation-audit-2026-10-09.md) for the final policy and checks.

All model response schemas use the SDK's Structured Outputs conversion while application Zod parsing remains strict. In particular, nested discriminated response blocks become provider-compatible `anyOf` schemas. If model processing fails before an RFQ draft reaches finalization, the reply says that this attempt submitted nothing and the person does not need to resend the brief. This reply is unavailable once finalization starts or the operation has an attempted/uncertain dispatch. Safe diagnostic metadata retains stage, category and HTTP status without provider bodies or private prompts.

The OAuth vocabulary now accepts explicit `crm.rfq:write`; enrollment still defaults to `crm:read` and refresh cannot enlarge grants. Signed-request ceilings already support this syntax but must explicitly include the new scope. Deploy the companion Context Engine branch and configure its receipt migration, scope migrations and separate write credential before enabling the tool. Deployment must verify current catalogue admission separately from pushing code.

Recovery returns the original receipt without another POST. If the original response could not be persisted, retain the uncertain operation for administrator reconciliation; never generate a new UUID just to retry a timeout. The journal is not an atomic transaction with Twenty. Undo requires a separately supported, currently authorized domain operation; it is never an inferred reversal of the original HTTP request.

If an attempt was explicitly not dispatched and has no earlier uncertain attempt, Ramesh shows the public error code and offers cancellation for a corrected proposal or a retry after temporary access/service recovery. It does not redisplay stored RFQ details or upstream messages. An earlier uncertain attempt continues to require recovery with the same operation, even when the latest attempt was not dispatched.

Direct RFQ creation now gives plain-language recovery messages instead of those legacy confirmation codes. For legacy or structurally invalid requests, a validation failure names only fixed public field labels; “cancel that RFQ attempt” retires the sole eligible unsent attempt before a source-preserving correction. “Retry” checks an existing uncertain submission and never creates a replacement. Historical client values and provider messages are not disclosed by these status replies. Legacy confirmation-based operations retain their original confirmation policy.

An initial uncertain save offers one check of the existing submission. After that check remains unresolved, or the recovery window expires, the reply directs the person to an administrator to check and resolve the existing submission. It does not suggest resubmitting or keep offering retry. Operation identity and dispatch behavior are unchanged.

Full setup, SOP evidence and extension boundaries are in Context Engine's `docs/crm-rfq-writes.md`. RFQ creation and Gmail drafts retain separate OAuth capabilities and recovery behavior in the shared write executor. Model-free tests cover exact source preservation, forwarded/historical selection, direct execution after review, legacy confirmation recovery and grant narrowing.

`delete_crm_rfq` supports deleting an owned agent-created opportunity after edits using its current version; `delete_crm_note` does the same for an owned agent-created note. Both move the actual record to CRM trash without permanently destroying it. This is separate from version-bound undo. Fresh domain reads supply the target and expected version; explicit authenticated direct execution policy supplies the runtime mode. The bot accepts the canonical `deleted` receipt and returns the verified target, with no automatic restore offer.
