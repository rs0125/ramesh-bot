# RFQ intake and response validation audit

The final creation policy is to capture the complete original brief, with optional structured enrichment. Missing location, size, units, contacts, budget or classifications must not prevent an explicitly requested save. This implements the user's instruction that everything need not be extracted because the description already contains it.

## Incident boundary

Read-only diagnostics for the October 9 requirement showed that both attempts stopped after staging a draft, before independent review and dispatch. Both durable operations remained `DRAFT` with zero dispatch attempts. Neither reached CRM. The supplied size range and locality were valid under the old intake rules too.

The shared formatter used raw Zod JSON Schema conversion. Adding discriminated text/CRM-card answer blocks introduced nested `oneOf`, which the provider's strict response format does not support. The installed OpenAI SDK reproduces the incompatibility offline. All production structured responses and evaluation response builders now use `zodTextFormat` through a shared helper, retaining application validation.

The original exception was reduced to `RUN_FAILED`, so the exact historical HTTP response cannot be recovered. The incompatible schema is a verified code defect at the failing boundary, not a recovered historical provider error. New traces retain only the failing stage, a fixed error category and HTTP status, excluding provider bodies, prompts, contacts and credentials.

Reference: [OpenAI Structured Outputs supported schemas](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas), and the installed `openai/helpers/zod` implementation.

## Implemented intake policy

Comparison with `whatsapp-logistics-bot/src/routes/whatsapp.js` and `CRM-Automations/src/services/rfq.service.js` established that the older flow forwards the original message, extracts available fields, removes empty values and assigns that message to `description`. The CRM does not require our previous phrase-by-phrase intake grammar. Its old asynchronous forwarding acknowledgement also does not prove a completed CRM save; the new workflow retains verified receipts and duplicate prevention.

| Concern                        | Final behavior                                                                                                                                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Original brief                 | Required, complete and verbatim. The bot copies selected stored sources; multiple messages join with exactly two newline characters. The 3,000-character source limit remains, with rejection rather than truncation.                                       |
| Location and requirement       | Optional text. Incomplete, informal, non-quantified or nonstandard briefs can be saved without extracting either field.                                                                                                                                     |
| Other text fields              | Optional. Empty/null values mean omitted. Ungrounded enrichment is left out while the full brief still saves. Budget need not be extracted; if supplied, retain its meaning and original billing terms.                                                     |
| Phone                          | Populate only a supported, unambiguous Indian mobile. Other numbers remain in the description and do not block creation.                                                                                                                                    |
| Classifications                | Optional typed values with optional supporting quotes. No guessed defaults; explicit false is preserved.                                                                                                                                                    |
| Numeric area                   | Optional conservative enrichment. Never map a range, bound, approximate value or detected clipped quantity to an exact numeric area. Quantity parsing cannot reject the whole create. The strict quantity grammar is isolated to edits of existing records. |
| Usage, parking and staff roles | Preserved in the original description. Internal supply POCs are not client contacts. Owner and creator remain the authenticated employee; a description does not perform assignments.                                                                       |
| Save receipt                   | Confirms preservation of the complete brief and shows the title returned by the successful create plus a verified CRM link. It does not reconstruct saved fields from proposed arguments. A replay without a title remains generic.                         |
| Questions                      | Resolve unclear intent, the intended source brief or an essential unsupported action. Do not ask for missing optional fields, exhaustive extraction or reformatting.                                                                                        |
| Edits                          | Continue to require an authorized current record, exact version and explicitly requested changes. Omission keeps existing values; requested null clears supported fields.                                                                                   |

The planner, worker, verifier, tool description and transcript evaluation expectations now follow this policy. A later “yes” or “retry” must not replace the actual brief. Optional incorrect arguments can be omitted during review while retaining the full source.

The protocol still checks allowed fields, types, bounded sizes, identity, permissions, source authorization, independent review and idempotency. Empty-field normalization precedes the receipt hash. Best-effort enrichment happens afterward: changing a nonempty proposed value conflicts with a reused UUID even if that value could not be mapped. Authenticated receipt lookup precedes current enrichment rules, preserving historical successful or uncertain operations.

## Adversarial coverage

Earlier passes found partial-number extraction, clipped bounds, country-prefix loss and rejection of ordinary wording. The final tests require capture to succeed while unsafe optional enrichment is withheld. These are no longer reasons to reject the full brief.

- `5,000 sqft` extracted from `25,000 sqft`, a range endpoint or a qualified minimum does not become an exact saved area.
- Unsupported mobile numbers and clipped foreign prefixes stay in the description without an invented Indian phone field.
- Ordinary forms such as `5000 sqft or more`, `Area-5000 sqft` and compact parking notes can be captured.
- An incomplete brief with no extracted fields creates one RFQ and preserves every original character, including tags, line breaks, roles and parking.
- Optional nulls, blanks and absent classification quotes do not become a questionnaire; explicit false survives.
- Skipped or invented optional values do not appear as successfully saved fields in the confirmation.
- “Yes” preserves the original source; retry after a preparation failure creates once; uncertain recovery uses the same identity without a second creation.
- Real PostgreSQL checks establish that RFQ and email-draft recovery commands cannot select or cancel each other, and uncertain dispatch cannot be cancelled as unsent.

## October 10 strict contracts and response handling

The user requested strict machine-consumed decisions and tool arguments, code-generated save receipts, separate authorization/factual checks, and investigation of the response anomaly before adding retries. These changes are local and have not been deployed.

- All tool declarations now use `strict: true`. A provider-only adapter closes objects and makes each wire property required, while decoding optional `null` values back to omitted business arguments. Optional nullable fields use `null` for omission and `{ "value": null }` for explicit clearing; supplied values use `{ "value": ... }`. Required values, `false`, zero, empty strings, nested values and nullable array items retain their original meaning. Original contract validation still runs after decoding, including constraints unavailable in the provider subset. No existing business schema, operation ID, receipt hash or durable payload is rewritten.
- Machine-consumed response schemas continue to use the SDK's strict Structured Outputs conversion. Their adapter now parses one final message rather than SDK-concatenated text. Explicit commentary is excluded; multiple candidate final messages, multiple content parts, refusal, truncation, invalid JSON and schema mismatch fail with fixed categories and redacted shape counts. No application formatter retry or heuristic JSON repair was added.
- A plain new-RFQ save can skip supplemental formatter inference. The code-owned proposal still passes independent review against the original request and sources. Only afterward does the write executor recheck authenticated access and return the authoritative code-generated receipt. Mixed requests, explanation requests and reviewer repairs keep composition. `receipt_only` is a presentation hint, never permission or proof of success.
